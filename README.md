# LimitLatch

Free MIT static API spend and rate-cap simulator. Open index.html directly, or serve this folder with any static server. Fork by copying these seven files and retaining LICENSE. No installation or npm dependencies. Test with `node --test` in this folder.

Enter policy and ordered event JSON, or click a labelled made-up example. Policy fields are daily, weekly, monthly (nonnegative integer minor currency units up to Number.MAX_SAFE_INTEGER), rpm (nonnegative calls per rolling minute), and maxAgeMs (maximum observation age). The page does not interpret currency. Reserve: `{ "type":"reserve", "id":"call1", "amount":50, "at":1000, "observedAt":1000 }`. Settle: `{ "type":"settle", "id":"call1", "actual":55, "at":1001, "observedAt":1001 }`. Time fields are nonnegative epoch milliseconds. Input order is preserved; a backwards clock is refused. Input bounds: 500 events, 100000 characters per input. Oversize input is refused, never truncated.

Daily/weekly/monthly mean trailing 24 hours/7 days/30 days, with interval (now − window, now]. Monthly is not a calendar month. Accepted reservations count toward calls; settlements do not. The rate boundary expires exactly at 60 seconds. Every outstanding reservation remains charged against every spend cap until settled, even after its timestamp leaves a window. At settlement its full actual amount replaces the reservation and counts from settlement time. Underestimates appear as positive drift. No pending amount is automatically abandoned or refunded.

An amount equal to a spend cap is allowed; the next positive excess latches admission. A zero spend cap permits zero-value calls subject to rate. rpm=0 refuses every reservation. Any denied reserve, malformed event or invalid amount/clock latches admission. Settlement can still record actual cost while latched. Duplicate IDs/settlements and unknown settlements are refused. There is no override or unlatch action. Starting a new simulation is a separate hypothetical ledger, never a reset of an actual guard.

All output is computed in memory from unverified input. The browser uses no storage, cookies, network calls, accounts or analytics. Nothing survives reload. This page controls no real API and has no effect on any real agent. It does not read provider balances, authenticate a ledger, provide distributed concurrency, durable accounting or reliably hold spend limits under late reporting. An overrun can exceed a limit; the simulation records the debt and closes future admission. General information only, not financial advice.

The pure core also exports createSession(policy, adapter), an experimental serialization contract exercised with in-memory fakes in Node tests. It waits for adapter.write and exact adapter.read read-back before acknowledging, serializes concurrent admissions, and keeps an uncertain reservation plus a latch in process memory. The page never calls it. Read-back equality is not proof of disk durability or authenticity; recovery after process loss is not implemented. Do not use this simulator as a production billing guard.

Original implementation written by AI agents at Manykiln. It is a stand-alone simulation of rolling caps, reservations and a sticky latch; it is not a port of the LimitLatch app's code and does not claim to behave the same way. Run `node --test` to check it.
